# 020 지식층은 규칙으로 판단하는 작은 루프로 둔다 — 그래프 DB · 벡터 DB · 온톨로지 스택을 넣지 않는다

> 상태: 확정 (2026-10-08, Julian 결정)

## 맥락

Julian 이 온톨로지 세미나(2026-10-07, 다섯 강의)를 듣고 물었다. ① 손으로 만든 지식맵을 온톨로지 · neo4j · 벡터 DB 로 바꾸면 무엇이
다른가 ② 기준 지식은 그냥 DB 에 두고 지식맵은 우리 아기에만 써도 되지 않나 ③ 대화가 길어지는데 대화방을 나눠야 하나.

확인한 사실: 승인된 L1 은 77개, 관계는 「항목 → 월령 · 분류 · 닫는 항목(covers)」 한 단계다. 우리 아기 탭의 지식 지도는 따로 쌓은
지식이 아니라 L2 기록을 영역 여섯으로 보여 주는 화면이다. 서버는 질문 한 문장과 기록(최대 30줄)만 받고 이전 대화는 받지 않는다.

## 결정

지식층을 **규칙으로 판단하는 작은 루프**(상황 인식 → 판단 → 행동, 모델은 문장만)로 유지한다. 정의는
[knowledge-layers](../architecture/knowledge-layers.md) 「이 지식층이 하는 일」. 기준 지식(L1)은 출처 달린 표(JSON, 나중에 Neon 표)에,
지식맵은 우리 아기(L2)에만 — 이미 그 구조다(「층 구조」). 대화는 한 타임라인으로 둔다(SPEC-ASK-10, decisions/009).

세미나에서 가져온 것은 도구가 아니라 규율이다: 용어를 한 표로 통일(「어휘」 절) · 승인된 지식은 어딘가에 닿아야 한다(task common/016) ·
근거 없는 답을 세어 빈 곳을 찾는다(task common/017) · 해석은 사람이 확인한 뒤 저장한다(task ask/008).

## 기각한 대안과 이유

- **벡터 DB(임베딩 검색)로 L1 검색 교체** — 수십~수백 항목에서 「비슷한 글」 검색은 「맞는 항목」 검색보다 정밀도가 낮다. 우리 규칙은
  「모델은 건네받은 항목만 인용」이라 다른 월령의 항목이 근거로 들어가면 그대로 답에 나간다. 질문마다 임베딩 호출(돈 · 시간)이 붙고,
  왜 그 항목을 골랐는지 설명이 안 된다. 다시 볼 신호는 근거 없음 로그(common/017)가 특정 분류에 몰릴 때 — 그때도 새 DB 가 아니라
  Neon 안의 pgvector 부터
- **그래프 DB(neo4j 등)** — 관계가 한 단계이고 수백 개라 그래프 질의가 필요한 질문이 없다. 서비스 하나(요금 · 비밀값 · 장애 지점)가
  늘어나는 값만 치른다
- **온톨로지 스택(OWL/RDF · 트리플 스토어 · 추론기)** — 4교시의 사다리(용어집 → 택소노미 → 시소러스 → 온톨로지 → 지식그래프)에서 우리는
  「택소노미 + 시소러스 + 규칙 몇 개」면 충분하다. 형식 온톨로지는 여러 조직 · 여러 시스템이 같은 뜻을 써야 할 때 값을 한다. 혼자 만드는
  앱 하나에는 무게만 더한다
- **지식맵에 기준 지식까지 올리기** — 참고층(모두에게 같음)과 사실층(우리 아기)은 갱신 주기와 승인 규율이 달라 한 저장소에 합치면
  엉킨다(knowledge-layers 「공통 유닛 계약」). 세미나 1교시의 사실층 · 해석층 분리와 같은 이유
- **대화방 나누기(Claude · ChatGPT 식)** — 그쪽이 나누는 이유는 모델이 대화 전체를 매번 읽기 때문인데 우리는 이전 대화를 보내지 않는다.
  나누면 「버디는 우리 아기를 아는 한 사람」이 도구가 되고, 기록이 가리키는 원문 바닥(sourceMessageId)이 쪼개진다. 긴 대화의 문제는
  목록 가상화 · 페이징(성능)과 「기록 → 그 대화」 「날짜 → 그날 대화」 점프(찾기)로 푼다
- **온디바이스 모델** — 따로 확정했다(backend 「비용 추정」, 2026-10-07): 의료 인접 답변에서 작은 모델의 지어내기 위험이 출처 원칙과
  부딪히고, 되는 폰이 최신 상위 기종뿐이다
