# 말콩(malkong) 문서 체계

> 두 가지를 Neuro 에서 본떴다 — **문서 하네스는 `neuro-spec`의 구조**를, **지식층은 Neuro 의
> Knowledge Foundation(K1~K4)**을 줄여서 가져왔다. 무엇을 가져오고 무엇을 두고 왔는지는
> [knowledge-layers](architecture/knowledge-layers.md) 첫 절에 적어 두었다. 가져온 것은 구조와
> 원칙이고, 회사 문서의 내용을 옮겨 오지는 않는다.

이 폴더가 설계의 정본이다. 흐름은 한 방향이다 (스펙 주도 개발의 표준 사이클을 따른다):

```
constitution (불변 원칙)
   → architecture (전체 WHAT) → menu-spec (메뉴별 SPEC + HOW)
   → task (계획·작업 단위) → 코드 → 검증 (완료 조건 대조)
```

| 문서 | 담는 것 | 갱신 시점 |
|---|---|---|
| `constitution.md` | 불변 원칙 — 제품 5 + 개발 4. 모든 SPEC 위에 있다 | 거의 안 바뀜. 바꾸면 changelog |
| `product/` | 제품 브리프 — 계기·컨셉·차별성·스토어 문구의 원천 | 포지셔닝이 바뀔 때 |
| `architecture/` | 제품 전체의 방향(main-design) · 지식층(knowledge-layers) · 서버/DB/LLM/기기 DB 스키마(backend) · L1 지식베이스 실체(l1-knowledge-base) · 앱↔서버 API(api-contract) | 방향이 바뀔 때만 |
| `menu-spec/` | 메뉴별 상세 설계(탭 넷 — main-design 「구조」). SPEC 문장(WHAT)과 구현 방법(HOW) | 기능이 정해지거나 바뀔 때 |
| `app-design/` | 디자인 시스템 · 기술 스택 · 코딩 스타일. 최신(SOTA) 근거 포함 | 스택·스타일 결정이 바뀔 때 |
| `decisions/` | 결정 기록(ADR) — 대안을 기각한 이유. 정의는 다른 문서가 소유 | 무게 있는 선택마다 |
| `task/` | spec을 코드로 만드는 작업 단위. 메뉴별 폴더에 누적 | 작업 시작·진행·완료마다 |

## SPEC ID 규칙

`SPEC-<메뉴>-NN` — 메뉴 코드는 `HOME` · `ASK` · `BABY` · `GROW` · `MY`. 번호는 메뉴 안에서 이어진다.
(`HOME` 은 홈 탭이 없어진 뒤에도 그 SPEC 이 버디 탭의 브리핑과 성장 탭의 이번 달로 이어져 코드를 그대로 쓴다)
task 는 반드시 하나 이상의 SPEC 을 근거로 가리킨다. 근거 없는 task 는 만들지 않는다.

## 문서 작성 규칙 (핵심 여덟)

1. **WHAT 과 HOW 를 섞지 않는다.** SPEC 문장은 시스템이 보장할 동작·제약·실패 조건만 적는다.
   내부 구현(컴포넌트·함수·라이브러리)은 HOW 절로 내린다. 구현을 바꿔도 SPEC 이 유지되면 잘 쓴 것이다.
2. **같은 내용을 두 곳에 적지 않는다.** 반드시 한쪽이 낡는다. 정의는 한 곳에 두고 나머지는 링크한다.
3. **덧대지 않고 정의를 갱신한다.** 바뀐 결정은 본문을 고치고, 이력은 문서 끝 changelog 에 한 줄만 남긴다.
   본문에 날짜 꼬리표·"v2 변경 요약" 표를 쌓지 않는다.
4. **SPEC 문장은 조건과 결과가 분명하게 쓴다** (EARS 형식):
   ```
   평시     ▸ <시스템>은 <무엇>을 해야 한다.
   조건 위반 ▸ <상태>일 때 <일이 생기면>, <시스템>은 <무엇>을 해야 한다.
   ```
   문장 하나가 나중에 테스트 하나가 된다. 흐름이 중요한 SPEC 에는 수용 시나리오
   (WHEN 상황 → THEN 결과)를 덧붙일 수 있다.
5. **결정하지 않은 것을 결정된 것처럼 쓰지 않는다.** 모호하면 지어내지 말고 문서의 「열린 질문」 절에
   남기거나 본문에 `미결:` 로 표시한다. 수치·권한·오류 정책을 임의로 채우지 않는다.
   `미결:` 이 달린 SPEC 으로는 task 를 시작하지 않는다.
6. **자연스러운 한국어로 쓴다.** 주어를 생략하지 않고, 한 문장에 하나의 내용만 담는다.
   "적절히·안전하게" 같은 기준 없는 말은 쓰지 않는다. "해야 한다 / 해서는 안 된다"로 의무를 분명히 한다.
7. **예시를 정책으로 승격하지 않는다.** 목업 데이터와 화면 시안은 예시일 뿐, SPEC 이 아니다.
8. **출처를 남긴다.** 육아·의료 내용은 출처 화이트리스트의 근거를, 기술 결정은 참고 자료 링크를 문서에 적는다.

## 작업 흐름

1. **specify** — 기능을 시작하기 전에 [constitution](constitution.md)과 해당 메뉴의 `menu-spec/` 을 읽는다.
   SPEC 이 없으면 먼저 쓴다.
2. **clarify** — SPEC 에 `미결:` 이나 열린 질문이 걸려 있으면 먼저 푼다(사용자에게 묻는다).
3. **plan + task** — `task/<메뉴>/NNN-<주제>.md` 를 만들고 근거 SPEC · 단계(큰 기능이면 기술 선택과
   손댈 파일까지) · 완료 조건을 적는다. task 는 한 번에 리뷰할 수 있는 크기로 쪼갠다.
4. **implement** — 코드를 만든다. 끝나면 `npx tsc --noEmit` 과 `npx expo lint` 를 통과시킨다.
5. **verify** — 완료 조건(SPEC 문장)과 실제 동작을 하나씩 대조한다. 구현한 흐름 그대로 믿지 말고
   화면에서 확인한다. 규모가 커지면 이 단계를 별도 세션(에이전트)에 맡긴다.
6. task 상태를 갱신하고, SPEC 과 실제가 달라졌으면 SPEC 을 고친다 — 코드에 맞춰 몰래 완화하지 않고
   달라진 이유를 적는다. 무게 있는 선택이었다면 `decisions/` 에 한 장 남긴다.

## 용어

| 말 | 뜻 |
|---|---|
| 말콩이 | 물어보기 탭의 agent 이름 |
| L1 / L2 | 공공 지식 층 / 우리 아기 지식 층 — [knowledge-layers](architecture/knowledge-layers.md) |
| 기록 / 요약 | L2 안의 사실 / 해석 구분 |
| covers | L2-기록이 완료 처리하는 L1 항목을 가리키는 연결 |
| 챙길 것 | 표준(L1) − 기록(L2) 차집합에서 나오는 홈 추천 |
