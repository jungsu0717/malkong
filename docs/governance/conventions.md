# 문서 체계와 작업 순서 — 모든 앱 공통

모든 앱은 같은 방식으로 설계하고 만든다(스펙 주도 개발). 이 문서가 그 방식의 정본이다. 앱마다 다른 것(메뉴 코드, 품질 검사 명령,
출처 규칙)은 그 앱의 `docs/README.md` 와 헌장에 둔다. 처음 육아버디(apps/malkong)에서 만들어 쓰던 규칙을 2026-10-14 에 여기로 옮겼다.

## 문서 흐름

설계 문서는 코드보다 먼저 읽는다. 흐름은 한 방향이다.

```
constitution (바뀌지 않는 원칙)
   → architecture (앱 전체의 설계) → menu-spec (메뉴별 SPEC 과 구현 방법)
   → task (작업 단위) → 코드 → 확인 (완료 조건과 실제 동작 대조)
```

앱마다 `apps/<앱>/docs/` 에 아래 폴더를 둔다. 틀은 [docs/_templates/](../_templates/) 에 있다.

| 문서 | 담는 것 | 고치는 때 |
|---|---|---|
| `constitution.md` | 바뀌지 않는 원칙. 모든 SPEC 보다 위에 있다 | 거의 안 바뀜. 바꾸면 changelog |
| `product/product-brief.md` | 왜 만드는지, 컨셉, 다른 앱과의 차이, 스토어 문구의 원천 | 방향이 바뀔 때 |
| `architecture/` | 앱 전체 구조, 서버와 데이터, 외부 연결 | 방향이 바뀔 때만 |
| `menu-spec/` | 메뉴별 SPEC 문장(무엇을 해야 하는지)과 구현 방법 | 기능이 정해지거나 바뀔 때 |
| `app-design/` | 디자인 시스템, 기술 스택, 코딩 스타일 | 스택이나 스타일이 바뀔 때 |
| `decisions/` | 결정 기록 — 다른 안을 버린 이유. 정의는 다른 문서가 가진다 | 무게 있는 선택마다 |
| `task/` | SPEC 을 코드로 만드는 작업 단위. 메뉴별 폴더 | 작업을 시작하고 끝낼 때마다 |

## SPEC 번호

- `SPEC-<메뉴>-NN`. 메뉴 코드는 앱의 `docs/README.md` 가 정한다. 번호는 메뉴 안에서 이어진다.
- 앱이 둘 이상이라 같은 메뉴 코드가 겹칠 수 있다. 다른 앱의 SPEC 을 가리킬 때는 앱 폴더 이름을 붙인다(예: `malkong SPEC-LOG-01`).
- task 는 반드시 하나 이상의 SPEC 을 근거로 가리킨다. 근거 없는 task 는 만들지 않는다.

## 문서 작성 규칙 여덟

1. **무엇(WHAT)과 어떻게(HOW)를 섞지 않는다.** SPEC 문장에는 앱이 지켜야 할 동작, 제약, 실패 조건만 쓴다.
   컴포넌트, 함수, 라이브러리 같은 구현은 HOW 절에 쓴다. 구현을 바꿔도 SPEC 이 그대로면 잘 쓴 것이다.
2. **같은 내용을 두 곳에 적지 않는다.** 한쪽은 반드시 낡는다. 정의는 한 곳에 두고 나머지는 링크한다.
3. **덧대지 않고 정의를 고친다.** 바뀐 결정은 본문을 고치고, 이력은 문서 끝 changelog 에 한 줄만 남긴다.
   본문에 날짜 꼬리표나 「v2 변경 요약」 표를 쌓지 않는다.
4. **SPEC 문장은 조건과 결과를 분명하게 쓴다**(EARS 형식):
   ```
   평시     ▸ <앱>은 <무엇>을 해야 한다.
   조건 위반 ▸ <상태>일 때 <일이 생기면>, <앱>은 <무엇>을 해야 한다.
   금지     ▸ <앱>은 <무엇>을 해서는 안 된다.
   ```
   문장 하나가 나중에 시험 하나가 된다. 흐름이 중요한 SPEC 에는 「상황 → 결과」 시나리오를 덧붙일 수 있다.
5. **정하지 않은 것을 정한 것처럼 쓰지 않는다.** 모호하면 지어내지 않고 「열린 질문」 절에 남기거나 본문에 `미결:` 로 표시한다.
   숫자, 권한, 오류 처리를 마음대로 채우지 않는다. `미결:` 이 달린 SPEC 으로는 task 를 시작하지 않는다.
6. **자연스러운 한국어로 쓴다.** 주어를 생략하지 않고, 한 문장에 한 가지만 담는다. 「적절히」, 「안전하게」처럼 기준 없는 말은 쓰지 않는다.
   「해야 한다 / 해서는 안 된다」로 의무를 분명히 한다. 루트 `AGENTS.md` 「하지 말 것 1순위」를 지킨다.
7. **예시를 규칙으로 올리지 않는다.** 목업 데이터와 화면 시안은 예시일 뿐 SPEC 이 아니다.
8. **출처를 남긴다.** 기술 결정에는 참고 자료 링크를, 사실 주장에는 확인한 곳을 적는다. 앱마다 더 엄한 출처 규칙이 있으면 그 앱 헌장을 따른다.

## 작업 순서

1. **SPEC 확인** — 기능을 시작하기 전에 헌장과 그 메뉴의 `menu-spec/` 을 읽는다. SPEC 이 없으면 먼저 쓴다.
2. **미결 풀기** — SPEC 에 `미결:` 이나 열린 질문이 있으면 먼저 Julian 에게 묻는다.
3. **task 만들기** — `task/<메뉴>/NNN-<주제>.md` 를 만들고 근거 SPEC, 정한 것, 손댈 파일, 완료 조건을 적는다.
   한 번에 검토할 수 있는 크기로 나눈다.
4. **구현** — 코드를 만든다. 끝나면 그 앱 헌장의 품질 검사(예: `npx tsc --noEmit`, `npx expo lint`, 서버 시험)를 통과시킨다.
5. **확인** — 완료 조건과 실제 동작을 하나씩 대조한다. 구현한 흐름을 그대로 믿지 말고 화면에서 확인한다.
   규모가 커지면 이 단계를 별도 세션(에이전트)에 맡긴다.
6. **정리** — task 상태를 고치고, SPEC 과 실제가 달라졌으면 SPEC 을 고친다. 코드에 맞춰 몰래 완화하지 않고 달라진 이유를 적는다.
   무게 있는 선택이었다면 `decisions/` 에 한 장 남긴다. 작업 단위로 커밋하고 푸시한다.
