# 지식층 설계

> status: draft | 작성: Julian & Claude | 2026-09-30

## 핵심 요약

**문제**: 표준 지식과 우리 아기의 사실을 한 덩어리로 두면, 답변의 근거를 댈 수 없고 개인화도 안 된다.

**해결**: 지식을 두 층으로 나누고, 우리 아기 층은 안에서 다시 사실과 해석으로 가른다.
사실과 해석을 한 칸에 섞으면 반드시 한쪽이 낡는다.

## 층 구조

| 층 | 무엇 | 성격 | 예 |
|---|---|---|---|
| **L1 공공 지식** | 월령별 표준 — 접종·검진 일정, 발달 이정표, 수유·수면 지식 | 모두에게 동일 · 정적 · **항목마다 출처** | "4개월 차 DTaP 2차" |
| **L2-기록** | 우리 아기의 관찰된 사실 | 사용자가 확인한 값 · 정정 가능 · 답변 근거로 안전 | 생일, 몸무게 6.4kg, 접종 완료, 수유 텀 3시간 |
| **L2-요약** | 질의 과정에서 추출한 해석·패턴 | 낡을 수 있음 · **시점 필수** · 재확인 대상 | "등센서가 심한 편", "수면 퇴행 중" |

사용자에게 보이는 구분은 L1(표준)·L2(우리 아기) 둘이다. 기록·요약 구분은 저장 구조와 신뢰도 처리에 쓴다.

## 규칙

```
출처   ▸ L1 항목은 출처 화이트리스트의 근거 없이 만들지 않아야 한다.
재서술 ▸ L1 본문은 원문을 복제하지 않고 뜻을 재서술해야 한다. 인용은 짧게, 출처 링크를 단다.
연결   ▸ L2-기록이 L1 항목을 완료 처리할 때는 covers 에 그 항목의 id 를 적어야 한다.
       기록 하나가 여러 항목을 완료 처리할 수 있다 — 같은 날 맞은 접종들, 또는 백신 종류 때문에
       필요 없어진 차수(로타 RV1 을 2차까지 맞으면 RV5 전용 3차도 함께 닫는다).
       홈의 추천은 이 연결의 차집합(표준 - 기록)에서 나온다.
시점   ▸ L2 항목에는 언제의 사실·해석인지(when)를 붙여야 한다. L2-요약이 오래되면
       그대로 단정하지 않고 "지난달 기준"으로 표시하거나 재확인을 요청해야 한다.
정정   ▸ L2-기록은 사용자가 고칠 수 있어야 하고, 고치면 그것을 근거로 한 추천이 따라 바뀌어야 한다.
저장   ▸ L2 는 아기 건강 정보이므로 초기에는 기기 안에만 저장한다. 서버 저장은 로그인·동의와 함께.
```

## 채워지는 경로

| 경로 | 층 | 비고 |
|---|---|---|
| 온보딩 (생일 1개) | L2-기록 | 이것만으로 L1 일정 전체가 아기 기준으로 계산된다 |
| 대화 중 되묻기 | L2-기록·요약 | 답변 전 1~2개만. 한 번 물은 것은 다시 묻지 않는다 |
| 이벤트 시점 요청 | L2-기록 | "검진 다녀오셨죠? 몸무게만" — 상시 기록 요구 금지 |
| (나중) 결과지 촬영 | L2-기록 | 자동화 후보 |

## 코드의 자리

`src/data/timeline.ts` — `L1Item`(= 지식베이스 항목 `@/data/l1`) · `L2Item`(= 기기 기록 `@/data/records`,
`covers: L1 id[]` · `whenLabel`) · `getGaps(월령, 기록)` · `buildTimeline(기록, 생일)`.
기록은 `record` 테이블(backend 기기 DB 절)에 있고 `records-context.tsx` 가 화면에 공급한다.
