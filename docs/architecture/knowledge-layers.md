# 지식층 설계

> status: draft | 작성: Julian & Claude | 2026-09-30

## 어디서 가져왔나 — 그리고 무엇을 가져오지 않았나

이 설계는 Neuro 의 **Knowledge Foundation**(지식 기질, K1~K4 모델)에서 뼈대를 가져왔다.
거기서 쓸 만한 것만 우리 규모에 맞게 줄였다.

| 가져온 것 | 우리 쪽 |
|---|---|
| **K4 도메인 지식** — "문서는 운반체, 지식이 실체", 파싱→추출→**승인** | **L1** — 공공 자료를 항목으로 증류하고 `status` 로 승인 게이트 |
| **K3 활동 지식** — 원문(episodic)과 증류본(semantic) **2층** | **L2** — 대화 원문은 `chat_message`, 증류본은 `record` |
| **참고층 vs 사실** — 업종 일반의 참고와 이 조직의 사실은 규율이 다르다 | L1(표준, 모두에게 같음) / L2(우리 아기의 사실) |
| **공통 유닛 계약** — 스토어는 나누고 계약·인터페이스만 공통 | `src/data/knowledge.ts` 의 `KnowledgeUnit` |
| 출처 없는 유닛을 만들지 않는다 | L1 은 `source`, L2 는 그 사실이 나온 대화 |

**가져오지 않은 것**: 표상·색인 전략(벡터·그래프 검색), K2 자산 지식(우리에겐 고객 자산이 없다),
저장소 4종 분리(둘로 충분하다), 조직 거버넌스 장치. 혼자 만드는 앱에 맞지 않는 무게다.
필요해지면 그때 다시 본다.

## 핵심 요약

**문제**: 표준 지식과 우리 아기의 사실을 한 덩어리로 두면, 답변의 근거를 댈 수 없고 개인화도 안 된다.

**해결**: 지식을 두 층으로 나누고, 우리 아기 층은 안에서 다시 사실과 해석으로 가른다.
사실과 해석을 한 칸에 섞으면 반드시 한쪽이 낡는다.

## 층 구조

| 층 | 무엇 | 성격 | 예 |
|---|---|---|---|
| **L1 공공 지식** | 월령별 표준 — 접종·검진 일정, 발달 이정표, 수유·수면 지식 | 모두에게 동일 · 정적 · **항목마다 출처** | "4개월 차 DTaP 2차" |
| **L2-기록** | 우리 아기의 관찰된 사실 | 사용자가 확인한 값 · 정정 가능 · 답변 근거로 안전 | 생일, 몸무게 6.4kg, 접종 완료, 수유 텀 3시간 |
| **L2-요약** | 질의 과정에서 추출한 해석·패턴 | 낡을 수 있음 · **시점 필수** · 재확인 대상 | "등센서가 심한 편", "수면 퇴행 중" |

사용자에게 보이는 구분은 L1(표준)·L2(우리 아기) 둘이다. 기록·요약 구분은 저장 구조와 신뢰도 처리에 쓴다.

### L2 는 두 층이다 — 원문과 증류본

위 표의 L2 는 **증류된 쪽**이다. 그 아래에 대화 원문이 그대로 남는다.

```
대화 원문 (chat_message)        ← 지우지 않는다. 되짚을 수 있는 유일한 바닥
    │  증류
    ▼
기록 · 요약 (record)            ← sourceMessageId 로 원문을 가리킨다
```

```
보존   ▸ 증류본을 만들 때 그것이 나온 대화를 가리켜야 한다(sourceMessageId).
재증류 ▸ 요약이 틀렸거나 낡으면 지우고 끝내지 않고, 원문으로 돌아가 다시 증류해야 한다.
       요약만 남기고 원문을 버리면 고칠 방법이 없어진다.
낡음   ▸ 오래된 요약은 stale 로 표시하고, 단정하는 대신 재확인을 요청한다.
```

### 두 층을 섞어 볼 때 — 공통 유닛 계약

답변과 화면은 L1·L2 를 함께 쓴다. 그때는 `src/data/knowledge.ts` 의 `KnowledgeUnit`
(id · layer · kind · 근거(origin) · 시점 · 신뢰도 · 낡음) 모양으로 본다.
**저장은 지금처럼 나눠 둔다** — 갱신 주기와 승인 규율이 다른 것들을 한 저장소에 합치면 엉킨다.

## 규칙

```
출처   ▸ L1 항목은 출처 화이트리스트의 근거 없이 만들지 않아야 한다.
재서술 ▸ L1 본문은 원문을 복제하지 않고 뜻을 재서술해야 한다. 인용은 짧게, 출처 링크를 단다.
연결   ▸ L2-기록이 L1 항목을 완료 처리할 때는 covers 에 그 항목의 id 를 적어야 한다.
       기록 하나가 여러 항목을 완료 처리할 수 있다 — 같은 날 맞은 접종들, 또는 백신 종류 때문에
       필요 없어진 차수(로타 RV1 을 2차까지 맞으면 RV5 전용 3차도 함께 닫는다).
       홈의 추천은 이 연결의 차집합(표준 - 기록)에서 나온다.
시점   ▸ L2 항목에는 언제의 사실·해석인지(when)를 붙여야 한다. L2-요약이 오래되면
       그대로 단정하지 않고 "지난달 기준"으로 표시하거나 재확인을 요청해야 한다.
정정   ▸ L2-기록은 사용자가 고칠 수 있어야 하고, 고치면 그것을 근거로 한 추천이 따라 바뀌어야 한다.
저장   ▸ L2 는 아기 건강 정보이므로 초기에는 기기 안에만 저장한다. 서버 저장은 로그인·동의와 함께.
```

## 채워지는 경로

| 경로 | 층 | 비고 |
|---|---|---|
| 온보딩 (생일 1개) | L2-기록 | 이것만으로 L1 일정 전체가 아기 기준으로 계산된다 |
| 대화 중 되묻기 | L2-기록·요약 | 답변 전 1~2개만. 한 번 물은 것은 다시 묻지 않는다 |
| 이벤트 시점 요청 | L2-기록 | "검진 다녀오셨죠? 몸무게만" — 상시 기록 요구 금지 |
| (나중) 결과지 촬영 | L2-기록 | 자동화 후보 |

## 코드의 자리

`src/data/timeline.ts` — `L1Item`(= 지식베이스 항목 `@/data/l1`) · `L2Item`(= 기기 기록 `@/data/records`,
`covers: L1 id[]` · `whenLabel`) · `getGaps(월령, 기록)` · `buildTimeline(기록, 생일)`.
기록은 `record` 테이블(backend 기기 DB 절)에 있고 `records-context.tsx` 가 화면에 공급한다.
두 층을 같은 모양으로 볼 때는 `src/data/knowledge.ts` 의 `unitFromL1` · `unitFromRecord` 를 쓴다.

## 나중에 볼 것

- **못 답한 질문 쌓기** — 근거가 없어 일반론으로 답한 질문을 남겨 두면, 다음에 L1 의 어디를 채울지
  추측하지 않고 알 수 있다. Neuro 쪽에서 "풀 수 있는 문제(K0)"를 정본으로 관리하는 것과 같은 발상이다.
  agent 를 붙일 때 로그 한 줄로 시작한다.
- **앱 사용법 지식** — "기록 어떻게 고쳐요?" 같은 질문에 답하려면 제품 자신에 대한 지식이 필요하다
  (Neuro 의 K1). 지금은 없다.
