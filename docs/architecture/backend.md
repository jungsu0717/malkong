# 백엔드 — 서버 · DB · LLM 파이프라인

> 근거: [constitution](../constitution.md) · [knowledge-layers](knowledge-layers.md) · [decisions/003](../decisions/003-backend-shape.md)

집에 두는 서버는 없다. 서버와 DB 는 전부 클라우드 관리형이고, 유저가 없을 때 비용이 0원에
수렴하는 구성으로 시작한다.

## 전체 구성

```
앱 (Expo)
 ├─ 기기 안: sqlite — 챗 이력 · L2 기록 (기본 저장소)
 └─ HTTPS → FastAPI 서버 (Cloud Run, scale-to-zero)
              ├─ 질문 라우터 (아래 LLM 파이프라인)
              ├─ L1 지식 검색 (월령·주제 필터)
              ├─ 사용량 제어 (일일 한도)
              └─ 운영 DB (Neon, 서버리스 Postgres) — 아래 「서버가 저장하는 것」
```

## 서버

```
평시 ▸ LLM 호출은 반드시 서버를 거쳐야 한다. LLM API 키를 앱에 포함해서는 안 된다.
평시 ▸ 서버는 요청이 없을 때 0원에 수렴하는 호스팅(scale-to-zero)에 둔다.
```

- 형태: **FastAPI 단일 경량 서버.** 역할은 셋 — LLM 프록시(라우팅 포함) · L1 지식 검색 · 사용량 제어.
- 실행은 **Cloud Run**, 상태는 **Neon**(서버리스 Postgres), 비밀값은 Secret Manager 에 둔다
  — 고른 이유는 아래 「무엇을 어디에 둘 것인가」.
- 코드는 같은 repo 의 `server/` 에 있다. 코드 구조와 규칙, 로컬 실행과 배포 명령은
  [server/AGENTS.md](../../server/AGENTS.md)가 정본이다.

### 서버가 저장하는 것 — 아기 데이터가 아니라 운영 데이터다

아기 데이터는 기기 안에 두는 것이 원칙이지만, **아래 다섯은 성격이 달라 서버에 있어야 한다.**
가족 공유를 하기 전에도 필요하다.

| 저장하는 것 | 왜 서버인가 |
|---|---|
| 일일 사용량 카운트 (디바이스 키별 · 0시 리셋) | 기기에 두면 앱을 지웠다 깔면 초기화된다 |
| 코호트 집계 (월령 밴드 × 주제) | 여러 사용자를 합쳐야 생기는 값이다 |
| 답변 피드백 | 서버가 받기로 한 것(SPEC-ASK-06) |
| 캐시된 답변 (라우팅 ②) | 모두가 나눠 쓰는 자산이다 |
| 운영자(가족) allowlist | 앱 안에서 풀 수 없어야 한다 |

```
금지 ▸ 아기 프로필·L2 기록은 이 DB 에 넣지 않는다. 가족 공유를 켠 사용자의 동기화 사본만 예외다.
```

### 무엇을 어디에 둘 것인가 (2026-10-02 조사)

| 자리 | 선택 | 이유 |
|---|---|---|
| 실행 | **Cloud Run** | 컨테이너형 서버리스 중 FastAPI 에 가장 맞는 선택으로 평가된다 — 0 으로 내려가면서도 진짜 컨테이너를 준다 |
| 상태 | **Neon** (서버리스 Postgres) | 쿼리가 없으면 컴퓨트가 0 으로 내려가 **노는 동안 0원**, 요청이 오면 바로 깨어난다 |
| 비밀값 | Secret Manager | LLM 키를 코드·앱에 넣지 않는다는 규칙 때문에 |
| 배치 | (나중) Cloud Scheduler | 캐시 사전 생성·집계를 서버에서 돌릴 때 |

- **Supabase 에서 Neon 으로 바꿨다.** Supabase 무료 티어는 한동안 안 쓰면 프로젝트를 재우는 방식이라
  깨어날 때 걸린다. Neon 은 컴퓨트만 내려갔다 올라와서 우리 "0원에 수렴" 원칙에 더 맞는다.
- **DB 를 두 번 고르지 않아도 된다** — 지금 운영 데이터를 Neon 에 두면, 가족 공유로 프로필·기록
  동기화가 필요해질 때 같은 Postgres 에 테이블만 더하면 된다.
- `주의:` Cloud Run 은 **요청을 처리하지 않는 동안 CPU 를 조인다.** 백그라운드 작업이 조용히 멈추는
  것이 흔한 실수다. 아침 브리핑은 기기에서 만들어 지금은 해당 없지만, 캐시 사전 생성처럼 서버에서
  도는 작업을 넣을 때 설정을 챙긴다.

조사 근거: [FastAPI 호스팅 비교 2026](https://www.pandastack.ai/blog/best-fastapi-hosting-platforms-2026/) ·
[백엔드 배포 도구 2026](https://northflank.com/blog/best-tools-to-deploy-backends) ·
[Neon vs Supabase 2026](https://dev.to/raxxostudios/supabase-vs-neon-choosing-a-serverless-database-in-2026-23n4)

| 리전 | asia-northeast3 (서울) | 사용자가 한국에 있어서 왕복 지연이 가장 짧다 |
| 최소 인스턴스 | 0 | 요청이 없으면 0원에 수렴해야 한다(이 절 첫 규칙) |

| 상태 확인 경로 | `GET /health` | `/healthz` 처럼 z 로 끝나는 일부 경로는 Cloud Run 이 예약해 두어 앱까지 오지 않는다 |

## DB — 두 단계

| 단계 | 어디에 | 무엇을 |
|---|---|---|
| 지금 | **기기 sqlite** (expo-sqlite) | 챗 이력 · L2 기록 · 아기 프로필. 서버 전송 없음 |
| 지금 | **앱 내장 + 원격 갱신** | L1 지식(월령별 표준). 크기가 작아 앱에 실어 나가고 서버에서 판만 갱신 |
| 지금 | **Neon** (서버리스 Postgres) | 운영 데이터 — 사용량·집계·피드백·캐시·allowlist. 아기 데이터는 넣지 않는다 |
| 가족 공유부터 | 같은 **Neon** 에 테이블 추가 | 아기 프로필 + L2 기록의 동기화 사본. 로그인·명시 동의와 함께만 |

```
평시 ▸ 챗 이력은 기기 안에만 저장해야 한다. 가족 공유를 켜도 동기화 대상은 아기 프로필과
      L2 기록으로 한정하며, 무엇이 올라가는지 사용자에게 보여야 한다.
```

가족 공유(한 아기를 여러 양육자가 함께 보기)가 서버 DB 를 도입하는 유일한 이유이자 시점이다 — SPEC-MY-05.

## LLM 파이프라인 — 질문 라우팅(폭포)

승부처는 모델 크기가 아니라 컨텍스트다. 구조화된 L1 + 우리 아기 L2 를 쥔 작은 모델이
이 도메인에서는 범용 챗봇보다 정확하다. 비용은 라우팅으로 막는다:

| 단 | 처리 | 비용 |
|---|---|---|
| ① 규칙 응답 | 접종 일정·월령 수치 조회, **위험 신호(SPEC-ASK-02)** — LLM 없이 템플릿 즉답 | 0 |
| ② 캐시 | 같은 월령대 단골 질문의 사전 생성·캐시 답변. 또래 질문 묶음(SPEC-GROW-05)이 이 캐시의 1차 공급원이자 소비자 | 0 |
| ③ 모델 | 고정한 모델 하나 + 검색된 L1 조각 + L2 컨텍스트로 합성 | 아래 상한 안 |

**모델은 하나로 고정한다** (2026-10-02, 사내 AI 담당 조언 반영). 처음부터 소형·상위 둘로 나누면
관리만 늘고, 답변 품질이 질문마다 들쭉날쭉해 신뢰가 깎인다. 질문에 따라 모델을 가르는 일은
트래픽이 생긴 뒤에 다시 본다.

```
평시     ▸ 위험 신호 판별은 모델에 맡기지 않고 ①의 규칙 필터가 선행해야 한다.
평시     ▸ ③의 공통 프롬프트(시스템·L1 컨텍스트)는 프롬프트 캐싱을 적용해야 한다.
조건 위반 ▸ 무료 사용자가 일일 한도를 넘으면, 앱은 보상형 광고 충전(정밀 답변)과 절약 모드
          (일반 기준 답변) 두 선택지를 제시해야 한다 — 아래 「일일 한도」 절이 정본.
```

### 세는 단위는 횟수, 막는 것은 토큰 (2026-10-02 확정)

토큰으로 세자는 안이 있었지만 **사용자에게 보이는 단위는 횟수로 둔다**. "오늘 남은 토큰 3,200"은
새벽에 지친 부모가 쓸 수 있는 말이 아니고, 질문마다 얼마가 깎일지 예측할 수 없어 불공정하게 느껴진다.
무엇보다 되묻기가 토큰을 먹으면 사용자가 되묻기를 미워하게 되는데, 되묻기는 우리가 일부러 설계한
핵심이다(SPEC-ASK-03).

비용이 들쭉날쭉한 원인은 답변 길이다. 그걸 서버에서 묶으면 **질문 1건당 비용이 거의 일정해져서
"10회"가 곧 비용 상한이 된다.**

```
평시 ▸ 서버는 한 답변의 최대 길이를 고정해야 한다.
평시 ▸ 모델에 넣는 컨텍스트에도 상한을 둬야 한다 — L1 조각 수와 L2 요약 길이.
평시 ▸ 하루 토큰 천장을 따로 두어, 길이 상한을 빠져나가는 이상 사용을 막아야 한다.
금지 ▸ 토큰 잔량을 사용자에게 보여주지 않는다. 사용자가 보는 단위는 질문 횟수뿐이다.
```
`미결:` 최대 길이·컨텍스트 상한·토큰 천장의 숫자 — agent 연결 task 에서 실제로 재보고 정한다.

### 일일 한도 — 10회 + 보상형 광고 최대 3회 (2026-10-01 확정)

```
평시 ▸ 한도는 ③이 만든 최종 답변(type=answer)에만 1회씩 차감해야 한다.
      차감하지 않는 것: ① 규칙 응답 · ② 캐시 응답(또래 질문 묶음 포함) · 되묻기(followup) 왕복 ·
      같은 clientMessageId 재시도 · 서버 오류 응답.
안전 ▸ 위험 신호(redflag) 응답은 한도와 무관하게 항상 나가야 한다. 한도 때문에 응급 안내가
      막혀서는 안 된다.
보상 ▸ 보상형 광고 1편을 끝까지 본 것이 검증되면 +1회, 하루 최대 3편(= 정밀 답변 하루 최대 13회).
      적립분은 그날 자정까지만 유효하고 이월하지 않는다.
소진 후 ▸ 한도를 다 써도 아예 막지 않는다 — **절약 모드**로 계속 답한다: ① 규칙·② 캐시는
      평소처럼 동작하고, 합성이 필요한 질문만 무료 티어 모델로 보낸다.
절약 모드 ▸ 무료 경로에는 L2 기록을 주입하지 않는다(개인 데이터를 학습 가능 티어로 보내지 않는
      원칙). 질문·월령·L1 조각만 보내고, 답변에 "우리 아기 기록 없이 일반 기준으로 답했다"를 표시한다.
조건 위반 ▸ 무료 티어 쿼터(프로젝트 전체 공유)가 그날 소진되면, 그때만 내일 0시 안내를 낸다.
평시 ▸ 집계와 리셋의 정본은 서버다(X-Device-Key 단위, 매일 0시 KST 리셋). 기기는 표시용 잔여만 캐시한다.
```

절약 모드는 **프로토 단계 정책**이다 — 무료 쿼터를 전체 사용자가 나눠 쓰므로 사용자가 늘면
유지되지 않고, 구독제 도입 시점에 재설계한다. 절약 모드 답변이 L2 없는 일반 기준이라는 품질
차이가, 광고 충전(정밀 답변)과 나중의 구독제가 매력적인 이유가 된다 — 일부러 둔 격차다.

운영자(가족) 기기는 아래 「운영자 기기」 절대로 한도를 적용받지 않는다 — 소진 개념 없이
항상 유료 모델 + L2 포함 정밀 답변이다.

미결: 캐시 무효화 주기 — agent 연결 task 에서 정한다.
API 의 구체 형태는 [api-contract](api-contract.md).

### 어느 모델을 쓰는가 — 가장 싼 모델부터 재서 고른다

```
평시 ▸ 운영 모델은 Gemini 3.5 Flash-Lite 다 (2026-10-02, decisions/008).
평시 ▸ 모델을 고르거나 바꿀 때, 그리고 프롬프트를 고칠 때는 같은 질문 세트(server/eval)로 다시 잰다.
      가장 싼 모델부터 재고, 통과 기준을 넘는 첫 모델을 쓴다.
```

- 통과 기준: JSON 형식 깨짐 · 지어낸 출처(SPEC-ASK-01) · 판단 요구에 진료 권유 빠짐(SPEC-ASK-08) ·
  위험한 조언이 모두 0건이고, 나머지 규칙(type, 수위, 되묻기 모양 등)이 90% 이상. 질문 세트와 채점 규칙의
  정본은 `server/eval/` 이다(task common/003).
- 사내 AI 담당 조언은 Claude Sonnet 급이었다. 지금은 재지 않았고 나중에 고려할 후보로 둔다 — 어댑터가 있어
  같은 질문 세트로 바로 잴 수 있다.

### 비용 추정 (2026-10-01, 한도 결정의 근거)

- 소형 모델(입력 $1·출력 $5/백만 토큰 대) 기준 질문 1건 ≈ 입력 ~3K 토큰(프롬프트 캐싱으로 대부분
  할인) + 출력 ~400토큰 = **약 5~7원**. Sonnet 급은 그 몇 배다.
  실측(2026-10-02): Gemini 3.5 Flash-Lite 는 입력 약 1,100토큰, 유료 가격으로 **1건 약 1원**이다.
- 활성 사용자 1명이 하루 10회를 전부 소형 모델로 써도 **월 1,500~2,000원**, ①②(규칙·캐시)가 절반을
  흡수하면 월 1,000원 안팎 — 배너+전면 광고 수익과 같은 자릿수라 상쇄 가능한 수준이다.
- 무료 크레딧: 주요 API 중 **Google Gemini 무료 티어**(Flash 계열, 속도 제한)가 넉넉해서
  개발·테스트 단계는 비용 0원으로 갈 수 있다. 출시 품질 모델은 유료로 확정한다.
- 온디바이스 sLLM(1~3B 탑재) 검토 — **도입하지 않음 권고**: 의료 인접 답변에서 소형 모델의
  환각 위험이 constitution 의 출처 원칙과 충돌하고, 모델 1~2GB 용량·발열 부담이 크다.
  저위험 작업(L2 요약 문구 생성)에 한해 나중에 재검토한다.

### 모델은 갈아끼우는 부품이다

```
평시 ▸ 모델 이름·API 키는 서버 설정값이어야 한다. 모델을 바꾸는 데 앱 업데이트가 필요해서는 안 된다.
```

- 각 회사의 **공식 SDK**(`anthropic`, `google-genai`)로 붙이고, 그 차이는 우리 어댑터 계약
  (`server/app/infra/llm/base.py`) 뒤에 숨긴다. 프롬프트와 `/v1/ask` 는 이 계약만 본다. 쓰는 모델은
  환경변수로 고른다. OpenAI 호환 API 로 묶지 않는 이유는 [decisions/007](../decisions/007-llm-adapter.md) —
  Claude 의 호환 계층이 JSON 형식 강제와 프롬프트 캐싱을 무시한다.
- Gemini 는 `store=False` 로 보내 대화를 Google 서버에 남기지 않는다.
- Claude 를 쓸 때는 Vertex AI(같은 GCP 프로젝트)로 부른다. 키 대신 서비스 계정 권한을 쓰고 결제도 GCP 로
  묶인다. 지금은 쓰지 않는다 — 나중에 고려할 후보다(task common/003).
- **"모델 고정"은 운영의 이야기지 코드의 이야기가 아니다.** 지금 쓰는 모델은 하나로 고정하되,
  바꾸는 데 앱 업데이트가 필요해서는 안 된다.
- 개발 단계 기본값: **Gemini Flash 계열 무료 티어** (인디 개발의 일반 관행).
  **주의 — 무료 티어는 입력이 제품 개선(학습)에 쓰일 수 있다. 실제 아기 데이터를 무료 티어로
  보내서는 안 된다.** 개발은 목업 데이터로 하고, 실사용 전환 시점에 유료(미학습) 모델로 바꾼다.

### 운영자(가족) 기기 — 광고·한도 면제

```
평시 ▸ 서버가 운영자(가족)로 지정한 디바이스 키에는 일일 한도를 적용하지 않아야 하고,
      앱은 광고를 보여주지 않아야 한다. 지정은 서버 allowlist 로만 한다(앱 안에서 풀 수 없다).
```

- 앱은 부팅 시 기기 자격(entitlements — 광고 여부·한도)을 받아 따른다([api-contract](api-contract.md)).
- 광고 정책상으로도 필수다: 본인 기기에서 실광고를 반복 노출·클릭하면 AdMob 계정 정지 사유라서,
  개발·가족 기기는 광고 면제 또는 테스트 광고 ID 로만 간다.

## 능동 브리핑 · 피드백 · 코호트 집계

**아침 브리핑(SPEC-HOME-06) — 두 단계.** 분석에 필요한 재료(L2 기록·L1 표준)가 전부 기기에
있으므로, 1단계는 **온디바이스 생성 + 로컬 알림**(expo-notifications 예약)으로 서버 없이 간다 —
비용 0 원칙과 일치. LLM 문구가 필요한 부분은 템플릿으로 시작한다. 서버 배치 생성(원격 푸시)은
가족 공유로 서버 DB 가 생기는 시점에 함께 도입한다.

**답변 피드백(SPEC-ASK-06).** 좋아요/별로예요 + 선택 의견을 서버로 보낸다. 쓰임새 둘 —
② 캐시로 승급할 답변 고르기, 프롬프트·모델 조정의 근거. 기기 식별자와 분리해 저장한다.

**코호트 집계(SPEC-GROW-05).**
```
평시 ▸ 서버는 /ask 요청에서 (월령 밴드, 질문 주제) 익명 카운트만 적재해야 한다.
      질문 원문·디바이스 키를 집계 테이블에 저장해서는 안 된다.
평시 ▸ 표본이 기준(k)보다 작은 묶음은 노출하지 않고 더 넓은 밴드로 합쳐야 한다.
```
`미결:` 질문 주제 분류 방법(규칙 vs 소형 모델) · k 값 — 코호트 task 에서.

**또래 기록 분포(나중).** 질문이 아니라 L2 기록의 분포를 보여주는 기능은 성격이 다르다 —
기기 안에만 두기로 한 L2 를 집계값이라도 서버로 보내야 하기 때문이다. 그래서 **명시적 동의를 받고
켜는 기능**이어야 하고(범주값만 · 아기 식별자 없이 · 무엇이 올라가는지 보여주고), 서버 DB 가 생기는
가족 공유 시점 이후에 다룬다. 동의 없이 기본으로 켜서는 안 된다.

## 기기 DB 스키마 (expo-sqlite)

```sql
CREATE TABLE baby (                        -- 아기 프로필 (당분간 1행)
  id          TEXT PRIMARY KEY,
  name        TEXT,                        -- 선택
  birth_date  TEXT NOT NULL,               -- YYYY-MM-DD. 월령·D+일수는 저장하지 않고 계산한다
  created_at  TEXT NOT NULL
);
CREATE TABLE record (                      -- L2 — 기록과 요약
  id                 TEXT PRIMARY KEY,
  baby_id            TEXT NOT NULL REFERENCES baby(id),
  kind               TEXT NOT NULL CHECK (kind IN ('기록','요약')),
  label              TEXT NOT NULL,        -- "수유 텀 3시간 · 160ml"
  covers             TEXT,                 -- 완료 처리하는 L1 항목 id 목록, JSON 배열 (홈 추천 차집합의 근거)
  when_label         TEXT,                 -- "D+86 질문에서" 같은 시점 표기
  source_message_id  TEXT,                 -- 어느 대화에서 나왔나
  stale              INTEGER NOT NULL DEFAULT 0,   -- 요약이 낡았다고 표시되면 1
  created_at         TEXT NOT NULL,
  updated_at         TEXT NOT NULL
);
CREATE TABLE chat_message (                -- 대화 — 단일 타임라인 (스레드 없음, 날짜로 구분)
  id          TEXT PRIMARY KEY,
  role        TEXT NOT NULL CHECK (role IN ('user','malkong')),
  content     TEXT NOT NULL,
  meta_json   TEXT,                        -- sources · followup · 저장된 record id 등
  created_at  TEXT NOT NULL
);
CREATE TABLE settings (                    -- 작은 설정값 (광고 제거 구매 사본 · 브리핑 시각 등)
  key    TEXT PRIMARY KEY,
  value  TEXT NOT NULL
);
CREATE TABLE inbox_card (                  -- 아침 브리핑 등 능동 카드 (SPEC-HOME-06)
  id           TEXT PRIMARY KEY,
  kind         TEXT NOT NULL,              -- briefing (후속: reminder 등)
  payload_json TEXT NOT NULL,              -- 할 일 · 챙기지 못한 것 · 상태 확인 질문
  read_at      TEXT,
  created_at   TEXT NOT NULL
);
CREATE INDEX ix_chat_created  ON chat_message(created_at);
CREATE INDEX ix_inbox_created ON inbox_card(created_at);
```

- 월령은 항상 `birth_date` 에서 계산한다 — 저장해 두면 낡는다.
- 사용량의 정본은 서버다. 기기에는 표시용 잔여 횟수만 캐시한다.
- 가족 공유 도입 시 `baby`·`record` 만 동기화 대상이 된다(SPEC-MY-05). `chat_message` 는 올라가지 않는다.
